# 0031 One view path below 100 %

Status: implemented
Reviewed: spec-reviewer, 2026-11-08
Depends on: 0001 (checkerboard), 0004 (zoom, Fit to Window), 0012 (Gradient), 0013 (selection), 0017 (text box), 0025 (the pixel contract's tests)

## Why
Below 100 %, a waiting gradient and a moved selection cost the picture's size per frame, not the screen's: at Fit to Window on an 8000 × 8000 picture about 390 ms a frame for a gradient and 165 to 173 ms a move for a selection (`docs/graphics-path-audit.md`, finding 1). Gradient types (Radial, Reflected) cost more per pixel, so this comes first. At the same time the pixel each screen pixel shows below 100 % is left to the graphics driver; this feature fixes it by one rule, the same for the picture, its previews and the pointer. Decided by JOD on 2026-11-08: sharp (one picture pixel per screen pixel, exact colors), and a budget of two frames.

How it meets P7: colors stay exact (P7.1: the view shows picture pixels, it blends none); below 100 % the view cannot magnify, and P7.2 says what it does there instead (amended with this spec, JOD 2026-11-08): REQ-0031-01's rule, which depends only on the zoom and the position in the picture; a preview and the put-down go through the same rule (P7.3); the same input gives the same view (P7.4).

## Requirements
- REQ-0031-01 (Pointer note, 0025's change of 2026-11-13: on a screen whose scale is not a whole number this rule is not met; the look there is not specified, REQ-0025-07.) While the zoom is below 100 %, each device pixel of the view shall show exactly one picture pixel, the one whose square holds the device pixel's center: counted from the picture's top-left device pixel, device pixel d shows picture pixel floor ((d + 0.5) × 100 / zoom) in x, and the same in y (the zoom counts device pixels, P7.2, so the screen scale does not enter; JOD, 2026-11-08), computed exactly in whole numbers (a center exactly on an edge between two pixels belongs to the pixel that starts there); in its exact color, a transparent pixel over the checkerboard as today (REQ-0001-11). Which picture pixel a device pixel shows depends only on the zoom and d, never on the scroll position or the window size. The picture covers the device columns whose named pixel exists (those with a named pixel less than its width), at least one; where that one column's named pixel does not exist (a picture narrower than one device pixel at the zoom), it shows the last pixel; the same for rows. The picture's shadow and handles lie at that edge (REQ-0009-02, REQ-0004-17).
- REQ-0031-02 (Changes how REQ-0025-03 is met below 100 %, not what it says.) The rule of REQ-0031-01 shall be the one rule for everything that shows picture pixels below 100 %: the picture, a waiting gradient, a moved or floating selection (inside and outside the picture), and an open text box; each shows, at a device pixel, the pixel the put-down writes at the picture pixel REQ-0031-01 names, and a float's part outside the picture its own pixel at that position (REQ-0013's float outside). A shape's preview keeps REQ-0025-03's exception (one row in every few beyond 3000 rows).
- REQ-0031-03 (Changes REQ-0025-06 below 100 %.) While the zoom is below 100 %, a pointer position, taken in device pixels (its logical position times the screen scale), anywhere over a device pixel of the picture shall map to the picture pixel that device pixel shows (REQ-0031-01); outside the picture, by the same formula, so the coordinates can be negative or beyond the size, as today (REQ-0004-09).
- REQ-0031-04 While a gradient waits or a selection is moved or held floating below 100 %, the work and the memory of a frame shall grow with the device pixels the view shows, not with the picture's pixels: at Fit to Window on an 8000 × 8000 picture in a 1920 × 1080 window at screen scale 1, the median frame (pointer event to painted frame, over three runs, at 60 Hz) while the gradient's end or the selection is dragged shall take at most 33 ms (two frames), and the memory the view holds for it at most 8 bytes per device pixel of the picture shown. This is a new row of the performance budgets, added by the Plan's ADR.
- REQ-0031-05 If the memory for a frame's view cannot be had, then that frame shall show the picture without the preview, by the scaling the picture's own tiles need no memory for (an exception to REQ-0031-01 and -02 for that frame), and the next frame tries again; nothing of the picture, the gradient or the selection changes, and nothing is shown to the user.
- REQ-0031-06 At 100 % and above nothing changes (REQ-0025-02 and its paths).

## Edge cases
- The grid, the tint, the outlines, the handles, the markers, the caret and the Magnifier's box: overlays, unchanged (REQ-0025-05).
- A zoom change or a scroll during a drag: the next frame is built for the new view.

## Out of scope
- A smoothed view below 100 % (JOD chose sharp, 2026-11-08). The later "Smooth shapes and brushes" option (`docs/specs/INDEX.md`, Phase 2) may change this view's rule when it is on (JOD, 2026-11-08); decided in that feature's spec.
- The put-down's own cost (it writes every pixel, as it must).
- 100 % and above, and a fractional desktop scale (125 %, 150 %): its own check, in `docs/phase2-plan.md`'s list before the first beta.

## Open questions

## Plan
**Approach.** Below 100 % the canvas builds the view it shows itself, as 0025 does for fractional zooms: one device pixel each, for the part of the picture the view shows, and draws it as one texture at device resolution. Each device pixel asks for one picture pixel, by one new core rule. Without a preview the pixel is read from the picture; with a gradient waiting or a selection moved or floating, it is the put-down's pixel at that picture pixel, made by the same core code as the put-down (the gradient's and the selection's lay, called for the sampled pixels only). The view is kept between frames while nothing changes (as 0025's `view_kept`). The picture's size on screen below 100 % follows the same rule (REQ-0031-01's column count), and the pointer maps by it.

**Files.** `src/core/view.{c,h}` (the rule, the column count, the pointer below 100 %); `src/core/gradient.{c,h}` and `src/core/selection.{c,h}` (lay a set of sampled pixels, if R1 needs it); `src/ui/canvas.c` (the view below 100 %, the previews' sampled pixels, the text box and the float outside through the view, the memory fallback, the content size); `docs/decisions/` (an ADR adding the budget row, REQ-0031-04); `docs/engineering.md` (the row); tests in `tests/core/test-view.c`, `tests/ui/test-window.c`; benchmarks `perf-0012`, `perf-0013` (a 2000 × 2000 case).

**Interfaces.**
- core, as built: `int easel_view_pixel_below (int d, int pct)`: floor ((2d + 1) × 50 / pct), in whole numbers, negative d included; `int easel_view_edge_below (int k, int pct)`: the first device pixel showing k or after, negative before the picture; `int easel_view_count_below (int size, int pct)`: the device columns of REQ-0031-01, at least 1; `easel_view_built_by_edges` true below 100 % at a whole screen scale; `easel_view_to_pixel` by the new rule below 100 %; `easel_view_content_size` below 100 %: the column count over the scale.
- ui, as built: `view_edge`, `view_cell`, `view_extent` in `canvas.c` (the edges from 100 % up, REQ-0031-01's rule below) for every reader of the view's geometry (the picture, the text box, the float outside, the shape preview, the grid, the keyboard marker, the handles); `append_view_by_edges` lays a waiting gradient's pixels itself below 100 % (`easel_gradient_lay`, one per device pixel); `append_view_of_selection` keeps the selection's trail at the view's size (`vtrail`, freed with the trail) and lays the new copies and the float each frame (`easel_selection_lay_range`); `gradient_preview` and `selection_preview` are not called below 100 %.

**Readers of what changes.** `easel_view_content_size`: the canvas's measure (the picture's size on screen, the scroll range), `easel_view_anchor` (zoom about a point), 0004's Fit to Window cases (AS-6: their sizes on screen, e.g. 5184 rows at 16 % now 829 device rows, which 0004's spec already names), 0009's margins and shadow, the handles (0004, 0015), the grid's lines below 100 % (0004 AS-11); `easel_view_to_pixel`: every press and motion, the status bar's position (0004 AS-8), 0025's AS-2 runs at 25 % and 50 %; the scroll-to-focus and thumbnail cases that convert positions.

**Constitution.** P7.1 exact colors (no blend); P7.2 as amended; P7.3 the preview's pixels from the put-down's own core code; P7.4 a rule of whole numbers; layering: the rule in `src/core`; P5: the budget row by ADR, measured before and after.

**Risks.**
- R1 Calling the gradient's and the selection's lay once per sampled pixel may cost more per pixel than the 33 ms allow (a 1920 × 1080 view is 2 million pixels). Probed in T001 with the core functions on the fit-zoom view of 8000 × 8000; fallback: a core function that lays a list of sampled columns for one row. **Probe, 2026-11-08** (`-O2`, the 800 × 800 view at 10 %, 640,000 pixels): the gradient's lay called once per pixel 10.2 ms, once per sampled row (the whole 8000-pixel row) 77.9 ms; a moved selection with no stamps 9.2 ms per pixel, 12.9 ms per row. Per pixel it is: no new core function for the gradient.
- R2 The selection's moved preview keeps a trail of stamps (smear) that its lay walks; its cost per sampled pixel grows with the stamps. Probed in T001 with a long smear; fallback: the trail's existing tile cache, sampled. **Probe, 2026-11-08:** with 209 stamps the lay costs 638 ms per pixel and 733 ms per row: every pixel walks every stamp. So the view keeps a sampled trail (the base and the stamps laid so far, one pixel per device pixel, 4 bytes each, within REQ-0031-04's 8) and each frame lays only the stamps added since (`easel_selection_lay_range`), about 10 ms a stamp at this view; the float is laid over it per frame. A zoom or a scroll during a smear rebuilds it once (about 600 ms at 209 stamps), as today's tile cache rebuilds at full size.
- R3 The canvas's size below 100 % changes by at most one device pixel (the column count against today's ceiling): readers above; checked by 0004's, 0009's and 0025's suites in T003.
- R4 (settled, JOD's go 2026-11-08; REQ-0031-01, AS-4, AS-5 corrected) Spec gap: REQ-0031-01's formula multiplies the zoom by the screen scale, but the zoom already counts device pixels (P7.2: zoom/100 device pixels per picture pixel), so at scale 2 it is wrong. Proposed: "floor ((d + 0.5) × 100 / zoom)"; AS-5: at scale 2, 50 % gives 1, 3, 5, 7, 9 and 25 % gives 2, 6, 10, 14, 18 (as at scale 1); AS-4 at scale 2: logical 0.3 (device 0.6) → 2, logical 0.6 (device 1.2) → 6.

Findings
- F1 (high, memory, user-visible) A picture narrower or shorter than one device pixel at the zoom (a 3 × 3 picture at 10 %, which Zoom Out reaches) covers one device pixel whose named pixel does not exist (pixel 5), and the view reads `img->px` past the picture's end for it; REQ-0031-01 says that pixel shows the last one. `as2_view_below_scrolled` checked only the canvas's width there, not the pixel shown. Proposed: every picture pixel the view names is held to the picture (at most its last one), in the view, the gradient's and the selection's sampled pixels; `as2` asserts the 3 × 3 case's pixel (2, 2). Fixed: the view, the gradient's and the selection's sampled pixels go through one rule held to the picture's last pixel; `as2_view_below_scrolled` red first (`0xffb4acb8 == 0xff0000ff`, a byte past the picture), then green.
- F2 (medium) The selection's kept trail (`vtrail`) is keyed by a hash that XORs the zoom, the view's place and its size shifted into overlapping bits: a scroll by 256 device pixels with a width one pixel different gives the same key, and the old trail would be drawn for the new view. Proposed: keep the zoom, x0, y0, width, height and the trail key as separate fields. Fixed so, by reading: the trail is laid again whenever any of the five differs; no test of its own (a collision needs two views a test cannot aim at; the 0031 cases that move the view while a selection floats pass).
- F3 (medium, coverage) REQ-0031-05 names the gradient and the selection; only the gradient's refused view is tested (AS-7). Proposed: the same case with a selection moved at 25 %. Fixed: `as7_view_memory_refused` has the selection case (refused: the white picture under the tint; with memory: the blue; put down as before). It passed at its first run (characterization); broken by hand (the selection's view allocating past the limit): red, `0x11 > 0xc0`.
- F4 (low, drift) The picture's handles below 100 % stand at the picture's width times the zoom, not at the edge of the device columns it covers (REQ-0031-01's last sentence): at most one device pixel apart (401 wide at 25 %: 100.25 against 100). Proposed: place them from the same count. Fixed: below 100 % the handles stand at the columns and rows the picture covers; `as2_view_below_scrolled` red first (`100.25 == 100`), then green.
